## 0. 默认假设（不同意任何一条请指出）

| # | 假设 |
|---|---|
| A1 | 只处理**合法获得、无 DRM** 的 EPUB；不做破解、不做分发 |

| A3 | 排版：**横排**（原书竖排则转换） |

## A. 必答（阻塞后续设计）

### ★Q01 能不能给我 1–3 本真实样书做开发与验收？
- 选项：A 马上给 / B 过几天 / C 没有，用青空文庫公版书自造
- **为什么问**：M0 的验收标准是"非文本节点逐字节不变"，没有真实书（带 ruby、脚注、插图、竖排）就无法验证。
- 推荐：A，至少一本正常横排 + 一本带注音/脚注的。

### ★Q02 你愿意投入多少人工？
- A 全自动（只抽检）——质量上限最低
- B 只确认术语与人物表（约 15 分钟/本）
- C B + 审"红旗段落"（约 1–3 小时/本）← **推荐**
- D B + 逐章通读校对（数小时到数天/本）
- **为什么问**：这是质量上限的唯一决定性变量，也决定要不要做审校 UI。

### ★Q03 成品形态
- 3a 语言：单语 / 双语对照 / 两者都要 → 推荐 v1 单语
- 3b 字形：简体 / 繁体 → 推荐简体
- 3c 排版：横排 / 竖排 / 跟随原书 → 推荐横排
- **为什么问**：直接影响 IR、CSS 覆盖层和审校界面。

### ★Q04 模型与预算
- 4a 模型来源：云 API 为主 / 本地模型 / 混合 → 推荐云 API + 关键段落用强模型
- 4b 单本预算上限：<10 / 10–30 / 30–100 / 不限（人民币）
- 4c 单本耗时预期：<1 小时 / 一晚 / 不限
- **为什么问**：决定多遍流水线的遍数、路由阈值和并发策略。

### ★Q05 第一本要翻的书是哪本？
- 需要：书名（日文原名）、大致字数、是否系列作、有无方言/字谜/双关/叙述性诡计
- **为什么问**：术语与人物表的冷启动要以它为样本；也决定风险策略的默认值。

## B. 产品形态

### Q06 运行形态
- A 纯 CLI / B 本地 Web（浏览器打开）/ C 桌面 App / D Calibre 插件
- 推荐：B（CLI 内核 + 本地网页审校）。理由：审校界面是核心，CLI 只能批处理。
- 追问：要不要"关掉电脑也能继续跑"（即部署到服务器/NAS）？

### Q07 是否开源
- A 私有 / B 开源（MIT/Apache-2.0）/ C 先私有，稳定后再开源
- 影响：开源要处理样本书版权、API key 配置、文档成本。

### Q08 一次性翻很多本，还是每次一本？
- A 单本 / B 排队批量（书库）→ 推荐 v1 单本，架构留批量。

## C. 输入

### Q09 书从哪来（可多选）

- 说明：D 涉及 DRM，本项目不做；B 需要额外 OCR 链路，v1 只留接口。
- 追问：你手上主要是哪种？

### Q10 书的形态
- A 单本长篇（10 万字级）/ B 短篇集（多篇独立作品）/ C 系列多卷
- 影响：短篇集需要"作品级"切分；系列需要跨卷共享人物与术语。

### Q11 竖排原书占比
- A 大部分 / B 一部分 / C 几乎没有
- 影响：转横排的 CSS 覆盖层优先级。

### Q12 有没有特殊结构
- 多选：插图 / 脚注 / 注音(ruby) / 表格 / 剧本体 / 书信体 / 作中作 / 目录多级
- 影响：IR 的边界用例优先级。

## D. 输出成品

### Q13 译注形式与密度
- 形式：A 脚注（推荐）/ B 文末注 / C 括注 / D 不加注
- 密度上限：每千字 ≤ 1 条 / ≤ 3 条 / 不限
- 追问：译者补充说明（如"此处原文为双关"）是否也用脚注？

### Q14 引号体系
- A 转中文引号：`「」→“”`、`『』→‘’`（推荐，符合简中出版习惯）
- B 保留日式 `「」`（有日味，但部分读者不适应）
- 追问：多层嵌套对话怎么处理（第三层用什么）？

### Q15 人名、地名、组织名
- A 日文汉字直接转简体（御手洗潔 → 御手洗洁）← 推荐
- B 保留日文汉字原字形（潔 / 渡辺）
- C 音译
- 追问：书名、章节标题里的专名是否同一规则？

### Q16 敬称怎么处理
- `さん`：小X / X先生 / 省略；`君`：X君；`様`：X大人 / X先生；`ちゃん`：小X
- 选项：A 按中文习惯自然化（推荐）/ B 保留日语敬称（X桑）
- 追问：敬称变化是线索时（突然改口），要不要加注？

### Q17 数字与单位
- 数字：阿拉伯（推荐）/ 中文数字
- 元号：首次出现括注公历（昭和 58 年（1983 年））← 推荐 / 只写元号 / 直接换公历
- 单位：保留（畳、坪）并加注 / 换算成平方米 / 只保留不注

### Q18 目次深度
- A 只到章 / B 章 + 节 / C 场景级（细）
- 推荐：与原书一致，不额外加深。

### Q19 插图与封面
- 插图：保留原图 + 翻译图注（推荐）/ 只保留图
- 封面：保留原封面（推荐）/ 中文重制 / 两者都放（封面 + 内页）

### Q20 主要用什么阅读器看？
- A Apple Books / B Kindle / C 微信读书 / D calibre / E 都要
- **为什么问**：Kindle 对 CSS 支持保守，会影响字体、缩进、注音的写法。

### Q21 是否内嵌中文字体
- A 不内嵌，用系统字体（文件小，推荐）/ B 内嵌（体积 +几 MB，显示一致）
- 追问：能否接受文件体积从 2MB 涨到 8MB？

### Q22 元数据与署名
- 作者名：保留日文原名（推荐）/ 译成中文
- 译者：写你的名字 + "AI 辅助" / 只写"AI 辅助翻译" / 不写
- 是否加免责声明（"仅供个人学习，请勿传播"）？

## E. 语言风格

### Q23 语体基调（最关键的一条）
- A 大众出版物（推荐）：通顺、克制、少翻译腔
- B 轻小说口语：短句、语气词多
- C 硬汉派冷硬：短促、少修饰
- D 文学化偏雅：书面、讲究节奏
- 追问：叙述部分与对话部分是否用不同基调？（推荐：是）

### Q24 忠实 vs 流畅
- A 保真优先，宁可略生硬（推荐）/ B 平衡 / C 可读优先
- **为什么问**：推理小说里"为了通顺补充信息"可能破坏线索。

### Q25 粗话、脏话、性暗示
- A 照译（按角色身份调节）/ B 整体弱化 / C 视角色而定（推荐）
- 追问：是否需要内容分级提示页？

### Q26 段落与句序
- A 允许合并同场景段落、调整句序（推荐，读起来像中文）
- B 严格保持原段落数（便于对照，但中文会碎）
- 追问：合并后是否要在审校界面标出"此处已合并"？

### Q27 章节标题
- A 直译 / B 意译 / C 直译 + 原文括注
- 推荐：A（标题常含线索，意译风险高）

### Q28 性与暴力描写的尺度
- A 照译 / B 淡化 / C 保留但加注
- 影响：是否需要在审校时标红。

## F. 推理小说特化

### ★Q29 诡计相关段落的策略
- A 保守：宁可读起来别扭，也不说死（推荐）
- B 通顺优先，允许适当明确化
- **为什么问**：这是"AI 翻译毁推理"的最大来源，也是本项目区别于其他工具的核心理由。

### Q30 谐音、字谜、回文、名字读法
- A 保留原文 + 括注 + 译注（推荐）
- B 尽量在中文里造一个等效双关（高风险，可能改谜底）
- C 直接意译，放弃双关
- 追问：你读到时，希望看到"原文 + 解释"，还是"中文里另造一个"？

### Q31 叙述性诡计中的性别隐藏
- A 回避代词（用名字/重构句子），接受偶尔别扭（推荐）
- B 用中性词绕（"那个人"）
- C 直接标性别（**强烈不建议**，等于泄底）
- 追问：如果中文实在绕不开，你希望加译者注提示"原文此处未标明性别"吗？（这本身也可能泄底）

### Q32 译注会不会泄底
- A 译注也要过审，禁止提前解释（推荐）
- B 允许在章末集中解释
- 追问：你希望译注是"随手可看"还是"折叠/文末"？
