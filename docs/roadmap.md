# 后续工作路线

> 2026-11-18。三本书已产出，M1 基本收口。这份文档回答：接下来做什么、按什么顺序、怎么验收。

## 一、判定原则

任何一项工作，先过三个问题：

1. **能不能减少人工？** 现在的瓶颈是"人要看的东西太多"，不是模型不够强；
2. **能不能验证？** 没有验收标准的功能不做（这条曾让"时间线检测"和"风险分级"被砍）；
3. **能不能复用？** 每本书都要重来的工作，优先做成流程。

## 二、P0：把现有流程做稳（不新增能力）

| # | 问题 | 做法 | 验收 | 状态 |
|---|---|---|---|---|
| P0-1 | 改一次 prompt 全部重翻，成本高 | 内容哈希缓存：`hash(原文+术语版本+prompt版本+模型)` 命中即复用 | 改一句 prompt，重跑时命中率 >70% | ✅ 已做（重复请求 0.18s 命中） |
| P0-2 | 报告互相覆盖 | 报告按书名分目录 `reports/<slug>/` | 三本书报告同时存在 | ✅ 已做 |
| P0-3 | 成本统计虚高 | 每篇只记本篇增量 | 统计值 = 实际调用量 | ✅ 已做（修订统计改为增量） |
| P0-4 | 没有自动回归 | `tools/regress.py`：黄金集重译 + 评分 + 与基线 diff | 一条命令出对比报告 | ✅ 已做（基线 4.47/4.57/4.13/4.20） |
| P0-5 | 术语/标题/目录链路各自造名 | 抽一个 `NameResolver`，所有产出链路统一走它 | 全书同一实体只有一种译名 | ✅ 已做（三本书残留变体 0） |
| P0-6 | 重建旧书时 IR 变更导致译文失配 | 译文块记录原文哈希，不匹配则标记待重译 | 重建不出现整段日文 | ✅ 已做（篡改哈希测试：检出 1 段并保留原文） |

## 三、P1：质量（直接影响阅读体验）

| # | 问题 | 做法 | 验收 |
|---|---|---|---|
| P1-1 | 译文偏"直译腔" | 增加 P4 润色：只改中文表达，禁止改事实；改动率上限 | 黄金集 fluency +0.3，保真不降 | ✅ 已做（A/B：流畅 +0.23，保真 +0.10） |
| P1-2 | 术语改了但旧段落不回填 | 术语变更时自动生成 fixes 并批量替换 | 改一处术语，全书生效 | ✅ 打包时 NameResolver 已覆盖 |
| P1-3 | 引号/括号配对没有校验 | 标点配对检查（整篇连检，支持跨段对话） | 三本书 0 违规 | ⚠️ 查出 7 篇待修 |
| P1-4 | 人名抽取靠模型，噪声大 | 用术语表 + 正则抽人名，替代 LLM 打分 | 一致性检查误报降到 <20% |
| P1-5 | 事实清单误报多 | 只对"红旗段落"跑，且要求给原文依据 | 误报率 <30% |

## 六、明确不做 / 缓做

| 项 | 原因 |
|---|---|
| 时间线矛盾自动检测 | 事件级抽取成本高，且专业小说时间线通常严谨；清单已够人工核对 |
| 表层特征风险路由 | 实测无效（覆盖 6% 只抓 15% 问题） |
| 别名自动定名 | 模型会重新发明（イナテン→稻田天），必须人工确认 |
| epubcheck 强制 | 本机无 Java；自研三重校验已够用，等有 CI 再说 |
| PDF/OCR 入口 | 与主线无关，用户暂无需求 |

## 七、建议顺序

```
第 1 批（稳）：P0-1 缓存 → P0-2 报告隔离 → P0-3 成本统计 → P0-4 回归脚本
第 2 批（准）：P1-2 术语回填 → P1-3 标点校验 → P1-1 P4 润色
第 3 批（顺）：P2-1 搜索 → P2-2 diff → P2-3 批量
第 4 批（快）：P3-1 并发 → P3-2 系列继承
```

每批做完，用**第四本书**做一次端到端验收（不作为新功能开发，只作为测试样本）。
